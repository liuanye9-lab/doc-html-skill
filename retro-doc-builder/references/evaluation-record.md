## 本 skill 的两个回归样本

| 样本 | 路径 | 期望结果 | 实测 |
|---|---|---|---|
| 正例 | `../assets/examples/qualify-block.html` | 静态与渲染均 PASS | 静态 ERROR 0 / WARN 0；渲染 820/640/360px 均 ERROR 0 |
| 负例 | `../tests/negative-block.html` | 静态命中全部禁令 + 飞书嵌入约束 | 静态 FAIL，30 ERROR |
| 色相负例 | `../tests/negative-multi-hue.html` | 注入第二、第三个色相时报错 | 稳定报 `出现 3 个彩色色相` |
| 实底负例 | `../tests/negative-too-many-solid.html` | 实底色块超过 1 处时报错 | 稳定报 `实底色块共 3 处，上限 1 处` |
| 计数负例 | 临时构造 | 声称数与实际条目不一致时报错 | 稳定报 2 ERROR |
| 飞书约束负例 | 临时构造 | 写死 px 宽 / 非法 height-mode 被拦 | 报 3 ERROR |

### 静态检查器 `check_blocks.py`

负例逐条命中（这是"规则真的在生效"的证据，不是"跑了一下没报错"）：

SaaS 蓝 ×6 · 红绿灯色 ×4 · 外链资源 · 外链样式表 · `<input>` · `<svg>` · `<script>` · 渐变 · 圆角 · 阴影 · 缺三个 meta · 多列缺 640px 塌陷 · `.mark` 重复 · emoji 当图标 · description 过短 · `border-left:3px` 多次 · 字号跨度不足 · **根容器写死 px 宽 ×2** · **非法 height-mode**

正例在同一套规则下零告警，说明规则不是靠"宽松"通过的。

### 渲染检查器 `render_check.py`

用注入缺陷的方式验证它真的会失败（一个永不失败的检查器没有价值）：

| 注入的缺陷 | 检查器反应 |
|---|---|
| 追加超长不可断词 | 三个宽度各报 1 处文字截断，ERROR 3 |
| 断点 `640px` → `1px` | 640/360px 下 c2 仍 2 列、c3 仍 3 列，ERROR 4 |
| 未注入（原正例） | ERROR 0 / WARN 0 |

## 视觉决策的实测依据

不是"看起来还行"，是量过的：

| 项 | 方法 | 结果 |
|---|---|---|
| 深绿 `#2C5545`（v2 时期）| 渲染后按语义色采样像素 | 仅 36 个采样点，15px 下读成黑色 → 废弃 |
| 克莱因蓝 IKB `#002FA7` | WCAG 对比度计算 | 对白底 10.69:1，但**与 ink 区分度仅 1.74** → 小字会读成黑 |
| 亮一档 `#0047D6` | 同上 | 对白底 7.31:1，与 ink 区分 2.54 → 小字用这档 |
| 蓝色是否真渲染出来 | 纯标准库解 PNG，按 `b > r+40` 采样 | 860×1680 截图采到 675 个蓝像素，400 个落在 IKB 色域 |
| 实底与点缀数量 | 检查器计数 | 正例：实底 1 处 · 彩色点缀 6 处 |
| 布局溢出 | iframe 真实宽度量 `scrollWidth` 与元素 `right` | 820/640/375px 全部零溢出（375px 实测 scrollWidth==clientWidth，超出元素 0 个）|
| 字号跨度 v1→v6 | 静态提取全部 `font-size` | 2.1× → **5.8×**（11–64px） |
| 宋体是否有真斜体 | 纯标准库解析 `Songti.ttc` name 表 | 8 个字面全是 Light/Regular/Bold/Black，**无 italic** |
| 820px 真实宽度 | 官方规格 + iframe 实测 | 飞书正文可用宽约 820px；此宽度下零溢出、多列保持 |

**六处值得记住的教训**（都不是靠读代码发现的）：

1. **测量假象**：先前用 `--window-size=360` 截图，看到标题被切、右侧贴边，判为溢出缺陷。改用 iframe 实测后 `scrollWidth == clientWidth`，根本没有溢出——是 Chrome headless 的 500px 视口下限造成的裁剪假象。**若当时按坏信号改 CSS，就会为了迎合测量错误而引入真缺陷。**

2. **照抄西文 recipe 会踩中文坑**：NYT / Monocle 的 dek 与 pull-quote 都用 italic serif，直接照搬写了 `font-style:italic`。实测本机宋体无真斜体字面，浏览器会做合成倾斜（把字形强行拉歪），属于劣质排版。改用 Light 字重 + 放大字号 + 收窄行宽建立层级。

3. **加新 class 会打破自己的检查器**：v2 给 `.sec` 加 `key/pos/neg` 修饰类后，计数检查器的切分正则 `<div class="sec"` 不再匹配，导致一个小节吞掉全篇，误报"声称 6 件实际 12 个条目"。**检查器的正则必须容忍修饰类**，否则每次扩展 CSS 都会制造假警报。

4. **CSS 特异性会静默吃掉颜色**：`.fill p{color:#fff}` 写在 `.bento p{color:var(--ink-2)}` 之前时被同特异性覆盖，实底卡上的字变深灰压深底，几乎读不到。更隐蔽的是 `.flag`（0,0,1,0）低于 `.bento p`（0,0,1,1），**源码顺序救不了低特异性**——必须写成 `.bento p.flag, p.flag, .flag`。改单色那次红色行内标记就这样静默变灰。

5. **`border-top` 粗线配圆角会长出翘角**：粗线与 1px 细线在圆角处斜接，渲染出突起的小三角。改用 `::before` 画绝对定位内嵌条 + `overflow:hidden`。

6. **上面这三条静态检查全绿**——只有看渲染截图才能发现。这是"静态通过 ≠ 好看"最硬的证据。

**一处自省**：v1 时检查器已报"字号跨度仅 2.1×"，我用"本块无 `.figure`，跨度天然较小"把它解释过去了——那是在给缺陷找借口。检查器报的是真问题，用例外解释掉等于关掉检查。

## 端到端验证：已真实跑通

网络恢复后完整跑了一遍 `init-draft → parse → +create → +update 修复 → +fetch 回读`。

**已验证**：

| 项 | 结论 |
|---|---|
| 六章骨架 + HTML 分流 | `parse` 返回 `assessment.status = passed`，28 个 block、1157 字 |
| `+create` | 成功，文档已生成，html5-block 拿到独立 block_token |
| 飞书嵌入约束 | 体积 20.2KB（上限 500KB）· 无破坏字符 · meta 三件套齐备 |
| 820px 真实宽度 | 零溢出、c2/c3 保持多列、三语义色均可辨认 |
| 回读校验 | 字面标签已清零、7 个 h2、3 个 callout、html5-block 在场 |

**这一跑抓出了 4 个只有真写才会暴露的缺陷**，全部已修复并写进 `feishu-html-block.md`：

1. `@path` 以 **CWD** 为基准，不是草稿目录 —— `parse` 报 `resource_preflight_failed`
2. `<text-bold>` **不在 schema 内**，被转义成字面文本，11 个段落显示出成对标签
3. `emoji-id` 不在 schema 内，静默丢弃
4. 缺 `<title>` 导致文档显示为 Untitled

**最重要的一条教训**：`+create` 返回 `ok:true` 时，这三个降级只出现在 `warnings[]` 里。**只看 `ok` 就宣布成功，会交付一份读者一眼就看出坏了的文档。** 必须逐条读 warnings，再用 `+fetch` 从另一条通道回读确认。

**仍未验证**：飞书 iframe 内 HTML 块的最终目视效果（GUI 两个浏览器平面本次都不稳定：bu 报 `BU_NO_ACTIVE_PAGE`/超时，cu 的 AX 树在 reload 后塌成退化结构）。块的存在性、alt、结构已由 `+fetch` 确认，但宋体在飞书环境是否落到宋体、`height-mode=auto` 的自适应表现，仍需人眼看一次。
