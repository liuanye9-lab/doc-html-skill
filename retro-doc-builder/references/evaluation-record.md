# 评测记录

## 回归样本

改校验规则时必须同时更新样本，否则规则改动没有证据。

| 样本 | 路径 | 期望 | 实测（v7） |
|---|---|---|---|
| 正例 ×5 | `../assets/examples/theme-{modern,swiss,editorial,gallery,mono}.html` | 静态与渲染均 PASS | **5/5 PASS，ERROR 0 / WARN 0** |
| 负例 ×10 | `../tests/make_negatives.py --check` 现场派生 | 每条命中对应规则 | **10/10 全部被拦住** |
| 全禁令负例 | `../tests/negative-block.html` | 命中禁令与飞书约束 | 稳定 FAIL |

**正例为什么用生成而不是手写 5 份**：内容必须完全一致，差异才只剩视觉，否则无法公平比较主题；而且正例内容一改，5 份手写副本会立刻漂移。`scripts/make_themes.py` 保证 5 套永远同源。

**负例为什么用派生而不是存死文件**：负例若是正例副本，正例一改就失效，且 8 个 14KB 副本没有信息量。派生保证负例永远跟着正例走。

## 只有看截图才发现的坑（静态检查全绿）

1. **反白文字被覆盖**：`.fill p{color:#fff}` 写在 `.grid p` 之前会被同特异性覆盖，深底上出现深灰字。base.css 已排好顺序，不要调整。

2. **低特异性救不了**：`.flag`（0,0,1,0）低于 `.grid p`（0,0,1,1），源码顺序无效。必须写 `.grid p.flag, p.flag, .flag`。第一次改单色时红色标记就是这样静默变灰的。

3. **粗线配圆角出翘角**：`border-top:3px` 配 `border-radius` 在上角产生斜接翘角。v7 把顶线画在无圆角单元上规避；带圆角元素要加顶线须用 `::before` 内嵌条。

4. **实心刻度条像涂黑**：4px 高实心分段条渲染出来像"删改条"，很脏。改 1px 发丝线后才读作"计数刻度"而不是"一块颜色"。

5. **深色区分度必须算**：不能凭感觉选深色，两次都是算完对比度才发现问题。

6. **测量假象**：先前用 `--window-size=360` 截图看到右侧贴边，判为溢出。改 iframe 实测 `scrollWidth == clientWidth`，根本没溢出——是 Chrome headless 约 500px 视口下限造成的裁剪假象。**若按坏信号改 CSS，就会为了迎合测量错误而引入真缺陷。**

7. **检查器会因作用域写错而误报**：v7 把 5 套主题放进同一份 base.css 后，色相统计一次性数到 5 个核心色，五套全部误报"多色相"；`--band` 又读到了媒体查询里的窄屏覆盖值。**修的是检查器的级联解析，不是 CSS。** 判断"是规则对还是产物对"这一步不能省。

## 同一个错误犯了两次

**第一次**：五套「模板」只覆盖颜色与字号，`t-modern` 与 `t-mono` 结构类属性为 0。用户：「不就是换了个颜色吗？」

我的修法是给每套加结构性 CSS（竖栏线、首字下沉、框线字符），并加了「主题须覆盖 ≥3 类结构属性」的规则。五套全绿。

**第二次，同一句批评**：「这 5 个方案还是差不多，没什么区别。我说的是整个形态、整体页面风格呈现的方式需要改变。」

这次找到了真正的根因，在 `make_themes.py` 里：

```python
html = SHELL.format(..., body=BODY)   # 五套共用同一个 BODY 常量
```

**五套主题读的是同一份 HTML 骨架，只切 body 的一个 class。** 所以无论 CSS 写多少条，五套的阅读顺序、组件构成、信息容器都完全一样——大号数字 → 四格指标 → 六条列表 → 引语带 → 表格。装饰换了，版面没换。

**而我的检查器只数 CSS 属性，天生看不到这一点**，所以两次都「全绿」。

修法：五套各写自己的骨架生成函数，各用自己的一组架构组件。判据也从「数 CSS 属性」改成「读 body 里的架构组件」，并加负例 `shared-skeleton`——把 `t-modern` 的 class 换成 `t-swiss` 而骨架不动，必须报错。

**教训**：连续两轮"看起来做了很多改动"却没解决问题时，不要继续加装饰，要去找**产物是怎么生成的**。根因在生成器里，不在 CSS 里。

## 一次严重的方向性错误

v7 第一版做了五套「模板」，但只覆盖了颜色与字号——`t-modern` 与 `t-mono` 的**结构类属性一条都没有**。用户看完截图直接判：「不就是换了个颜色吗？我的意思不是换颜色搭配。」

**这是对的，而且是我自己该发现的**：我当时甚至写了「五套模板」的文档，却没验证过它们在结构上到底差在哪。事后跑一行统计就看出来了——五套里两套结构覆盖为 0。

修法不是加更多颜色，是给每套找**结构签名**：瑞士的竖栏线与左栏槽、编辑部的真双栏流与首字下沉、画廊的展签式标签倒置、苹果的居中成栈与药丸标签、档案的框线字符。

**并把它变成可检查的规则**：主题必须覆盖 ≥3 类结构属性，否则 ERROR。负例 `color-only-theme` 专门守这条。**光靠自觉不行——上一版就是自觉失效的产物。**

## 两处自省

1. v1 时检查器已报"字号跨度仅 2.1×"，我用"本块无巨数，跨度天然较小"解释过去了——那是在给缺陷找借口。**检查器报的是真问题，用例外解释掉等于关掉检查。**

2. 加"尺寸编码优先级"规则后，它第一件事就是警告我自己写的正例全是等宽单元。**规则抓住作者本人才说明它有效**，据此把"高层支持"提为通栏 `c4`、"账号或数据没就绪"提为 `c3`。

## 端到端验证：已真实跑通

`init-draft → parse → +create → +update → +fetch` 完整跑过，文档已推进到 revision 11（v3→8、v4→9、v5→10、v6→11），四次均 `success` 且 `warnings: []`。

**这一跑抓出 4 个只有真写才会暴露的缺陷**，全部已修并写进 `feishu-html-block.md`：

1. `@path` 以 **CWD** 为基准，不是草稿目录 → `parse` 报 `resource_preflight_failed`
2. `<text-bold>` **不在 schema 内**，被转义成字面标签显示给读者
3. `emoji-id` 不在 schema 内，静默丢弃
4. 缺 `<title>` 导致文档显示为 Untitled

**最重要的教训**：`+create` 返回 `ok:true` 时，这些降级只出现在 `warnings[]` 里。**只看 `ok` 就宣布成功，会交付一份读者一眼看出坏了的文档。** 必须逐条读 warnings，再用 `+fetch` 从另一条通道回读确认。

另：每次 `block_replace` 都会生成**新的 block_id**，所以每轮都要先 `+fetch` 取当前 id 再替换。
