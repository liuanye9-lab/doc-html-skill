# Retro Doc Builder｜复盘文档生产线

复盘文档的价值不在"记录发生了什么"，而在**下一个人能不能照着做**。

前者是记录，后者是资产。这条区分决定了本 skill 的每一条规则。

## Critical：三条硬规则，违反即返工

1. **按决策顺序组织，不按时间顺序。** 时间顺序（先 A 后 B 再 C）只能让人知道发生了什么；决策顺序（为什么做→凭什么判断→期待什么→怎么做→效果→改什么）让人知道自己该在哪一步做什么判断。
2. **必须有反向清单和失败清单。** 没写"什么情况别做"和"哪些没跑通"的复盘，是宣传材料不是复盘。这两项是可信度的来源，不是可选项。
3. **易变信息留正文，稳定结构进 HTML5 Block。** HTML 块改起来要重出整块，正文改起来只改一行。分错了后续每次更新都要付代价。

## 执行路径 R0–R5

### R0 取材：先确认拿得到什么

复盘写不好，九成是素材不够而不是文笔不够。开工前先盘清六类素材，缺哪类直接问用户，**不要用合理推测填充**：

| 素材 | 用途 | 缺了会怎样 |
|---|---|---|
| 量化前后对比 | 第五章的骨架 | 效果只能写形容词 |
| 现场原声 / 证言 | 可信度的主要来源 | 变成自说自话 |
| 失败与没跑通的部分 | 第五、六章的可信度装置 | 读起来像宣传稿 |
| 时间线 / 议程 | 第四章的执行细节 | 复用者不知道怎么排 |
| 判断依据 | 第二章的准入框架 | 复用者不知道适不适合自己 |
| 会后动作与进展 | 第五章的收口 | 停在"气氛很好" |

**口径纪律**：数字必须来自素材原文或可复现计算。素材里没有的，写"当时未归档"并说明影响，**不要估算，不要留空当作没这回事**。原文档里"问卷满意度分布当时没归档，暂时拿不出来"就是正确写法——主动交代缺口比假装完整更可信。

**⛔ 出闸**：六类素材逐项标注「有 / 部分有 / 没有」，且"没有"的已问过用户或已确认写成缺口。

### R1 骨架：六问一条决策链

固定六章，**顺序不可调**。每章只回答一个问题：

| 章 | 回答 | 必须包含 |
|---|---|---|
| 一 为什么做 | Why now | 当时的处境 + 为什么选这个方案而不是替代方案 |
| 二 凭什么判断能做 | Qualify | **信号**（值不值得做）+ **前提**（做不做得成）+ **劝退**（什么情况别做） |
| 三 期待什么 | Define success | 分层期待，每层写"靠哪个环节实现 + 怎样算拿到" |
| 四 怎么做 | How | 流程 → 机制 → 经验 → Checklist → 坑 |
| 五 效果怎么样 | Evidence | 量化 → 成果与未跑通 → 原声 → 后续进展 |
| 六 回头看 | Learning | 做对的 N 条 + 要改的 M 条，**每条要改的都带「下次：」具体动作** |

**第二章的信号/前提二分是本骨架最锋利的地方，不要合并成"适用条件"**：信号差一点可以一起创造条件；前提缺一项就该劝客户先补齐再定时间。合并了就失去指导力。

**第二章的"前提"与第六章的"要改"必须互为正反面**——同一张清单的两种写法。写完后交叉检查：第六章每条"要改"，第二章是否有对应"前提"？

**⛔ 出闸**：六章齐全 + 第二章三段（信号/前提/劝退）都有内容 + 第六章每条"要改"都带下次动作 + 已做正反面交叉检查。

### R2 分流：什么进 HTML，什么留正文

逐块判断，**这一步决定文档后续好不好维护**：

| 去处 | 判据 | 典型内容 |
|---|---|---|
| **HTML5 Block** | 结构稳定 + 有对照/并列/时序/分层关系 + 需要视觉编码 | 判断框架、时间轴、五步法、Checklist、KPI、成果矩阵、双栏对比、复盘对照 |
| **正文** | 易变 + 需要论证语气 + 需要随时可编辑 | 后续进展、商机动态、材料索引、议程取舍的解释、口径声明 |

正文另外必须有三处：

- **顶部密级 callout**：内部沉淀的边界声明（能不能外发、证言能不能对外引用）
- **导读 callout**：告诉不同读者怎么读（"只想拿执行清单就直接翻第四章和第六章"）
- **数据前的预防针**：第五章开头声明"这是单次真实结果，不等于可承诺的标准效果"

**⛔ 出闸**：每块内容都已标注去处 + 三处正文必需项已就位。

### R3 选结构：先判信息类型，再选视觉形态

**不要套模板，要判类型。** 逐块问一句"它是哪种关系"，再查表：

| 信息类型 | 视觉结构 | 模板 class |
|---|---|---|
| 块报头（每块必备） | 巨大章节号 + 三段式 | `.hero` + `.kicker` + `h1` + `.dek` |
| 摘要网格（尺寸编码优先级） | bento | `.bento` + `.c1`~`.c4` + `.r2` |
| 卡面轻重分档 | 顶线粗细 | `.cell-hd` / `.cell-acc` / `.cell` / `.cell-q` |
| 并列同权（N 条经验） | 竖排条目组 | `.stack` + `.row` |
| 多维对比（方案 A vs B） | 表格 | `<table>` |
| 核对清单 | 假复选框 | `ul.check` |
| 关键指标 | 巨大数字 | `.fig` |
| 行内警示 | 强调标记 | `.flag` |
| 进度 / 分段 | 灰底黑条 | `.bar` / `.seg` |
| 原声引用 | 上下双线 | `.quote` |
| 小节分段 | 文字 + 底线 | `.sec` / `.sec.acc` |
| 全文唯一爆点 | 深底反白 | `.mark` |
| 收口脚注 | 顶线小字 | `.foot` |

结构清单与可直接复制的代码见 `references/block-library.md`。视觉规则见 `references/visual-system.md`。**动手写 HTML 前必须先读 visual-system.md**，否则会滑回 AI 默认审美。

需要一个完整的真实块做参照时，看 `assets/examples/qualify-block.html`（第二章"开展条件判断"，含信号/前提/劝退/本例对照四段，自带完整样式，可直接改内容复用）。

**⛔ 出闸**：每个 HTML 块都已指定信息类型与对应结构 · 同一类型全文只用同一种结构 · 每块有且只有一个视觉重心。

### R4 落地：写入飞书文档

按 `lark-doc` 的 online-doc 分支执行（从零创作走创建工作流：Presentation Decision → `init-draft` → 写 XML → `parse` → `+create`）。HTML5 Block 的写入方式、`alt` 语义要求、meta 头三行、飞书硬约束见 `references/feishu-html-block.md`。

四条不可省：

1. 每个块的 `alt` 必须是**完整语义描述**（不是"图1"）——大纲视图、全文搜索、AI 读取、无障碍全靠它降级
2. `<meta name="use-iframe" content="true">` + `<meta name="html-box-height-mode" content="auto">` 必须有
3. 每个块自带完整 `<style>`，**不依赖任何外部文件**
4. **按 820px 设计与验收**——飞书文档正文可用宽度约 820px，不是 1000px+；根容器只能用 `100%`，不得写死 px

**⛔ 出闸**：`python3 scripts/check_blocks.py <目录>` 零 ERROR。

### R5 交付前渲染自检

**不要只看代码就宣布完成。** 必须真实渲染看一眼：

```bash
python3 scripts/check_blocks.py <html目录>                  # 静态
python3 scripts/render_check.py <html目录> --out <截图目录>  # 渲染
```

`render_check.py` 用本机 Chrome 在 1000 / 640 / 360px 三个宽度渲染每个块，检查：横向溢出、文字截断、多列是否在 640px 塌陷、语义色是否真的出现在像素里、墨量占比是否失衡。窄宽度经 iframe 测量——**Chrome headless 视口有约 500px 下限，直接 `--window-size=360` 会产出"文字溢出"的假警报**，据此改 CSS 反而会引入真缺陷。

**另外必须补一次 820px 渲染**（飞书正文真实宽度，是最主要场景）：

```bash
python3 scripts/render_check.py <html目录> --widths 820,640,360 --out <截图目录>
```

脚本只能测机械问题，**截图必须实际打开看**，确认四件事：字号层级真的拉开了、克莱因蓝在小字上仍能辨认出蓝色而不是黑色、发丝线没有压过文字、每块有一个明确的视觉重心。

逐项确认：交付载体已给出可点击链接 · 数字与素材一致 · 失败清单在场 · 缺口已交代。

**⛔ 出闸**：两个脚本均零 ERROR + 820px 与移动端截图均已实际查看。

## 视觉方向：黑白灰 + 克莱因蓝点缀（v6）

复盘文档要让人**一眼看出重点在哪**。所以视觉的核心不是配色，是**让尺寸承担层级**。

纯白纸 + 发丝线 + 留白，主色只有黑白灰。**唯一点缀色是克莱因蓝 `#002FA7`**；实底色块整块最多 1 处，蓝色只作点缀（粗线 / 小标签 / 单个数字），不做彩色实底卡片。

**蓝色必须分两档**：真 IKB `#002FA7` 用于 3px 粗线与实底；小字（11–13px）必须用亮一档 `#0047D6`——真 IKB 与近黑的区分度仅 1.74，小字上会读成黑色。唯一权威 token 源是 `assets/base.css`，**整段复制进每个块，不要改数值、不要加新色**。

动手写 HTML 前**必须先读 `references/visual-system.md`**，否则会滑回等分卡片墙。

### 四条不可违背

| # | 原则 | 做法 |
|---|---|---|
| 1 | **尺寸编码优先级** | 每个 `.bento` 至少一个跨列更大的主单元。**全等分等于普通卡片墙，白付复杂度成本** |
| 2 | **相邻区块不得同高** | bento 网格 ↔ 竖排 `.stack` ↔ 深底 `.mark` 交替 |
| 3 | **字号金字塔** | 巨数 44px → 报头 32px → 卡内标题 16px → 正文 13.5px → 标签 11.5px，跨度需 ≥2.5× |
| 4 | **少用色块** | 实底（`.fill`/`.mark`）合计 ≤1 处；彩色只作点缀 ≤6 处。**色块堆多了就是杂乱**，层级交给字号、留白、顶线粗细 |

### 十条禁令（命中即返工）

| 禁 | 原因 |
|---|---|
| 米黄 / 暖纸底色 | 用户明确否决；一律纯白 |
| 通用 SaaS 蓝 `#3370FF` | AI 默认色，无身份 |
| 任何渐变 | AI slop 头号特征 |
| `box-shadow` | 靠发丝线与留白建立层次 |
| 小圆角 1–9px | 14px 圆角是签名，小圆角退回普通卡片 |
| 全等分卡片网格 | 尺寸不编码优先级就没有层级 |
| emoji / ✓ × ! 字符当图标 | 字符不是图标 |
| 第二个强调色（绿 / 蓝 / 橙 / 紫任一） | 语义已由尺寸表达，再用颜色编码一遍就是杂乱 |
| 多块实底色块并置 | 每加一块就削弱其余所有块；实底只留 1 处 |
| `border-top` 粗线配圆角 | 上角会出现斜接翘角；改用 `::before` 内嵌条 |
| 外链字体图片图表库 · `<script>` · `<svg>` | iframe 内会慢、会被拦、会失效 |
| 中文 `font-style:italic` | 中文无真斜体，会触发合成倾斜 |

### 一个必须记住的实现坑

`.fill p{color:#fff}` 写在 `.bento p{color:var(--ink-2)}` **之前**会被覆盖，实底卡上的字变深灰、压在深底上几乎读不到。base.css 已排好顺序，**不要调整这两段先后**；改完必须重新截图确认实底卡上的字是白的。

同类第二个坑：`.flag` 特异性（0,0,1,0）低于 `.bento p`（0,0,1,1），**源码顺序救不了低特异性**，必须写成 `.bento p.flag, p.flag, .flag`。

## 硬红线

- 只用当前用户身份，权限不足时说明需要加权，**不得换路径绕过**
- 客户证言、成果链接对外引用前必须取得授权，文档内需写明这一约束
- 不硬编码凭据、Token、内网 ID
- 不把估算数字写成实测数字；口径不明时标注来源与限制

## 改本 skill 之前

两个校验脚本的规则都有回归样本背书（正例 `assets/examples/` + 负例 `tests/`）。**改校验规则必须同时更新这两个样本**，否则规则改动没有证据。已有的实测依据与踩过的坑见 `references/evaluation-record.md`——尤其是窄屏验证那条，避免重复犯。

两个配色纪律负例由脚本从正例派生，改完正例后重新生成并自验：

```bash
python3 tests/make_negatives.py --check
```
